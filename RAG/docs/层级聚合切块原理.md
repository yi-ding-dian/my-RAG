# 层级聚合切块（Hierarchical Chunking）原理

> 本文档说明 my-RAG 知识库「层级聚合切块」的原理、生成流程与参数。
> 对应代码：`backend/normative/chunker.py`（`HierarchicalChunker`）；
> 标题层级还原见 `backend/normative/heading_llm.py`。
> 切块方式标识：`hierarchical`（前端「层级聚合切块」）

---

## 一、背景：这个算法为什么会出现

### 1.1 目标场景：写作规范的层级文档

企业规范性文档（调试说明书、操作规程、技术手册）有一个共同特点：

```
一、配置工具                      ← 章（几十页）
  1.1 工程数据配置                 ← 节
    1.1.1 业务管理员               ← 小节（常常只有两三行）
      1.1.1.1 应用配置
        ……正文 + 截图……
```

- **层级深**：动辄四五层，层级本身就是作者的语义组织
- **小节短**：最底层小节常常只有几十到几百字，配上截图
- **正文配图密集**：一个操作步骤配一张界面截图是常态

对这类文档，"一个块"的理想形态是**一个小节（或几个短小节的聚合）**——语义自足、尺寸适中。

### 1.2 通用切块：尺寸对了，语义碎了

通用递归切块（`naive`）按字符数等长切分，在这类文档上的典型症状：

```
块 3：……点击【应用配置】选项卡，显示当前工程配置的
      ↑ 块首是半句话，读者不知道这是哪一节
块 4：1.1.1.2 设备逻辑条件          ← 标题落到块中间/上一块尾部
      单击【五防应用配置】……
```

- 块边界与章节边界无关 → **标题与正文被拆散**、块首是"半句话"
- 一个块可能横跨两个小节 → 检索命中后**无法定位到具体章节**

### 1.3 自顶向下按标题切：语义对了，尺寸失控

`title` / `parent_child` 走的是另一条路：**自顶向下**——先按大纲找到标题边界，再在章节内部按字符数切。

这解决了语义问题，但尺寸反过来失控：

| 情况 | 自顶向下的结果 |
|---|---|
| 小节只有 200 字 | 自成一块 → **远小于 chunk_size，浪费召回位** |
| 小节有 5000 字 | 还得在内部二次切 → 又回到"半句话开头"的老问题 |

**根本矛盾**：块边界应当是**语义边界**（标题位置），块大小应当**贴近预算**（chunk_size）——而自顶向下的切法只能二选一：边界听标题的，大小就不受控；大小听预算的，边界就不在标题上。

### 1.4 绕不开的前提：PDF 解析后标题层级全丢了

这个算法建立在一棵**章节树**上——层级不对，树就是错的，整个算法失效。而现实是：

MinerU 解析 PDF 时，**把所有标题行统一输出为 `##`**（2 级）。真实的层级信息没有消失，而是**藏进了标题的编号里**：

```
## 一、配置工具          ← 实际是 1 级（章），但 # 数量是 2
## 1.1 工程数据配置       ← 实际是 2 级（节），# 数量还是 2
## 1.1.1 业务管理员       ← 实际是 3 级（小节）
```

更麻烦的是无编号标题里还混着**伪标题**——正文中的强调行被误判成标题，如「注意事项:」「安装流程:」，它们不是章节边界。

所以走 `hierarchical` 时通常要配一层**层级还原**（`backend/normative/heading_llm.py`）：

- **带编号的标题**：按编号体系规则确定性定级（零成本、结果稳定）
- **无编号的标题**：交 LLM 判（附「前文最近的带编号标题及其层级」作定位参考）

> 实测某 627 个标题的技术手册：全量交 LLM 需要 19833 token / 252 秒；
> 混合方案只用约 1/4 成本，且层级一致率很高——带编号那批规则本来就能算，没必要问模型。

还原后的层级通过 `heading_levels` 参数传入切块器（见第四节第 6 条）。

**什么时候才真的会走 LLM 分层**（三条全满足，见 `backend/services/ingestion/service.py`）：

1. 切块方式为 `hierarchical`；
2. 解析引擎**不是** `docx_struct`——docx 结构解析直读 OOXML，`#` 层级本来就精确，再跑 LLM 纯属浪费；
3. 系统配置的「标题分层模型」（`chunking.heading_llm_model`）非空，**且**该标识能在 LLM 模型列表里查到完整配置（含 api_key）。

未满足时不阻塞入库：**回退规则分层**（按标题编号推断），并在日志留痕说明原因。

## 二、核心思想：自底向上的章节树聚合

**不先定大块，而是从小节开始往上问一句话：「这棵子树装得下吗？」**

```
                  一、配置工具
                 ╱            ╲
        1.1 工程数据配置      1.2 系统设置
         ╱        ╲                │
   1.1.1 业务管理员  1.1.2 参数    ……（很短）
        │
   1.1.1.1 应用配置（正文 300 字）
   1.1.1.2 设备逻辑（正文 500 字）
```

自底向上逐层判断：

```
① 1.1.1.1（300 字）装得下 → 一个单元，且可上浮
② 1.1.1.2（500 字）装得下 → 一个单元，且可上浮
③ 两者合起来 800 字，仍在预算内 → 上浮到 1.1.1 合并
④ 1.1.1 + 1.1.2 合起来超预算 → 停在这里，1.1 内部拆成两个块
⑤ 1.2 很短 → 但不能跟 1.1 合（同属一章，章内可合）……
```

**产出的块**：

```
┌─ 块 1 ─────────────────────────────┐
│ 一、配置工具 > 1.1 工程数据配置        │ ← 标题链前缀（自带章节上下文）
│ > 1.1.1 业务管理员                   │
│ ## 1.1.1.1 应用配置                  │ ← 块首就是自己的标题
│ 单击【应用配置】选项卡下的……           │
│ ## 1.1.1.2 设备逻辑条件               │
│ 右键点击表格中的每一行……               │
└────────────────────────────────────┘
┌─ 块 2 ─────────────────────────────┐
│ 一、配置工具 > 1.2 系统设置           │
│ ……                                  │
└────────────────────────────────────┘
```

**一句话**：**块边界永远是标题（语义不乱），块大小自然贴近预算（尺寸不失控）**——
自顶向下二选一的那个矛盾，自底向上两个都要。

## 三、生成流程

```
文档全文
  │ ① 识别标题（_iter_headings：ATX + 纯文本标题样式，保护区间内不算）
  ▼
  │ ② 还原层级（可选，heading_levels 外部传入）
  │     · 覆盖从 `#` 数量得到的层级
  │     · level=0 的伪标题不进树（不是章节边界），但文本仍留在正文里
  ▼
  │ ③ 建章节树（_build_tree，栈式：父节点 level 严格小于子节点）
  ▼
  │ ④ 分组（_groups）
  │     · 章级标题（chapter_level，默认 1 级）各成一个聚合组
  │     · 组间永不合并；文首第一个章级标题之前的内容 = 独立「前言组」
  ▼
  │ ⑤ 组内三件事（每组独立执行）
  │     a. 自底向上收集单元（_collect_units）  ← 算法核心
  │     b. 纯标题单元粘合（_glue_heading_units：标题不单独成块）
  │     c. 贪心装箱（_pack）：每块尽量接近 chunk_size，边界落在单元之间
  ▼
  │ ⑥ 块首拼祖先标题链（_with_heading_chains）
  ▼
块列表
```

### 核心：单元（unit）是什么

`_collect_units` 返回的是「**贪心装箱的最小整体**」：

```python
if 整棵子树装得下(chunk_size):
    return [(node.start, node.end)]          # 一个单元，可继续上浮参与父级合并
else:
    return [直属正文] + [各子节点的单元展平]   # 边界落在子节点之间
```

因为**装箱不会把单元拆开**，块边界天然落在子树 / 子节点之间——这就是"标题与正文永不被拆散"的机制保证，而不是靠事后修补。

### 超长单元怎么办

子树自身超预算、且没有更细层级可聚合时（比如一个没有子节点的长正文），该单元整个交给装箱阶段**二次切分**：段落 → 句子 → 硬切逐级降级（见第四节第 3 条）。

装箱时有个细节：超长单元切出的**最后一片**不会单独成块，而是作为当前块起点继续向后贪心——避免"超长内容尾部剩一小片"变成碎片块。

## 四、关键设计（为什么这么定）

### 1. 合并不跨章级标题

`chapter_level`（默认 1 级）是**不可跨越的硬边界**：章与章之间永不合并，章内可以一路聚合到底（整章只有 200 字也并成一个块）。

**理由**：章级标题是文档最稳定的语义边界。跨章合并会让块同时携带两个主题，检索命中后无法定位到具体章节。

### 2. 块长度按**有效内容**计

图片引用（markdown `![]()` 与 HTML `<img>`）**不计入** chunk_size 预算。

**理由**：图片 URL 是资源引用而非语义内容。长哈希路径会吃光配额，把正文逼得提前断块。

另设**真实长度硬上限**（`chunk_size × 4`）兜底图片密集块的真实体积——有效长度在预算内、但真实长度爆表的块不再合并。

### 3. 超长兜底二次切：段落 → 句子 → 硬切

逐级降级，**保护区间（表格 / 代码块 / 图片引用）在每一级都是原子**，不被切开（超长表格宁可整块输出，项目既有语义）。

### 4. 块首带祖先标题链

块首拼接 `祖先 > 父 > 自己` 的标题链，**检索命中后不必回查原文即可判断归属**。

链由本模块按章节树直接生成，而非复用 `common.add_heading_paths`——后者判断"块首自带标题"用的正则是 `^#{1,6}\s+\S`，只取到标题的**首字符**，再拿首字符去标题链里匹配自然匹配不上，导致以标题开头的块几乎补不出祖先链。本算法的块恰恰几乎都以自己的标题行开头，且树已在手，按树取链更准也更省。

拼接规则：块首就是自己的标题行 → 只补**祖先链**（自己的标题已在块首第一行，拼全链会重复）；块首不是标题行（如兜底二次切的续接片）→ 补**整条链**，让块凭空多出所属章节信息。

### 5. 偏移契约

`Chunk(text, char_start, char_end)` 中 `text` 恒等于 `full[char_start:char_end]`——拼标题链前缀时**只改 text、不改偏移**（与项目既有做法一致）。测试断言依赖这条：切块结果可随时按偏移回原文校验。

### 6. 外部层级表（`heading_levels`）

应对第一节 1.4 的层级丢失问题：由外部（如 `heading_llm` 的混合层级表）传入每个标题的真实层级，覆盖从 `#` 数量得到的层级。与标题识别结果按顺序一一对应，`level=0` 表示"不是标题"。

### 附：overlap 的落点（与其它切块器不同）

`overlap` **只在兜底二次切分内部生效**（被强制切断的连续文本，与 `recursive` 的续接语义一致），**聚合块之间不回移起点**。

**理由**：聚合块的边界本身就是章节语义边界（子树 / 章节）。人为回移起点会让块首不再是它自己的标题，标题链前缀与块首标题错位——为了补一点上下文，反而破坏了整套语义结构。

## 五、与其它切块方式的对比

| | 通用 naive | 标题 title | 父子 parent_child | **层级聚合 hierarchical** |
|---|---|---|---|---|
| 切法方向 | 按字符等长 | 自顶向下按标题 | 自顶向下（父块聚合章节 + 子块） | **自底向上聚合子树** |
| 块边界 | 字符位置 | 标题 | 父：章节 / 子：章节段内 | **标题（子树 / 子节点之间）** |
| 块大小 | 贴合预算 | 由层级决定，失控 | 父块无上限 / 子块贴合 | **自然贴近预算** |
| 短小节 | 被切碎 | 自成小块（浪费） | 父块兜住 | **并入父级，不浪费** |
| 长小节 | 被切碎 | 内部二次切 | 子块承担 | **内部二次切（兜底）** |
| 章节上下文 | 无 | 块首标题 | 父块（检索时返回） | **块首标题链（自带，两层）** |
| 依赖前提 | 无 | markdown 层级准确 | markdown 层级准确 | **章节树准确**（PDF 需先还原层级） |
| 适用场景 | 常规文档兜底 | 结构文档 | 长章节型文档（合同 / 规章） | **写作规范的层级文档**（说明书 / 操作规程） |

**与 `parent_child` 的定位差异**（最容易被混淆的一对）：

- `parent_child` 是**两层结构**：小块负责"找得准"，父块负责"答得全"，检索命中子块后把整个父块塞给 LLM
- `hierarchical` 是**单层结构**：块本身就力求语义完整、尺寸适中，不需要"父块"这个额外层级
- 前者适合"章节很长、需要整章上下文"的文档；后者适合"小节短、章节层级深"的规范文档
- 两者都需要准确的标题层级；`hierarchical` 因为整棵树都要用，对层级错误的**敏感度更高**

## 六、参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `chunk_size` | 取 `chunking.chunk_size` | 块大小预算（按**有效内容**计，图片引用不计入） |
| `overlap` | 取 `chunking.chunk_overlap` | 仅作用于超长兜底二次切分内部（见第四节附） |
| `chapter_level` | 1 | 不可跨越的章级标题层级（1~6）。文档没有该级标题时整篇作为一个聚合组，不设强制边界 |
| `heading_levels` | 无 | 外部层级表（可选），应对 MinerU 全 `##` 输出；通常由 `heading_llm.hybrid_levels` 生成 |
| `add_heading_path` | 开 | 是否给块首拼接祖先标题链 |

**配置项**（`chunking.heading_llm_model`，系统配置页可设）：

走 `hierarchical` 且解析产物层级不可靠（非 docx 结构解析）时，用于重新分层的 LLM 模型标识。
空 = 不做 LLM 分层，只用编号规则分层。运行时动态读取，改配置即生效。

---

## 七、产出保证（测试断言依赖）

- 每块 `text == full[char_start:char_end]`（拼了标题链前缀的块只多一个前缀行）
- 块按原文顺序、区间互不重叠（overlap 续接仅在兜底二次切分内部，同组同段内）
- **任何块区间内部不含章级标题**（章级边界永不跨过）
- 表格 / 代码块 / 图片引用不会被切开

## 八、适用与选择（前端联动）

### 8.1 什么时候能选

| 入口 | 可选条件 |
|---|---|
| 智能解析向导 | 文档**有标题结构**（`structure.has_headings`）或引擎建议为 `docx_struct` 时才出现该选项 |
| 解析配置弹窗 | 所有走解析器的文档（pdf / docx / doc）都开放 |

### 8.2 解析方式 ↔ 切块方式的联动

- **智能解析向导**：切块方式与增强开关的默认值由后端决策矩阵统一给出
  （`backend/services/smart_parse/`）——解析引擎建议为 `docx_struct` 且有标题结构时，
  主推荐就是层级聚合切块，父子分块降为备选。向导的「推荐解析路径」面板、Step2 的
  推荐徽标、Step2 的默认选中**三处都从同一份 `parse_plan` 派生**，不会各说各话。
- **解析配置弹窗**（手动模式）：切到「结构解析」且切块方式**仍是默认值**（`naive`）时，
  自动改用层级聚合切块；用户**显式选过**的其它切块方式（如父子分块）不被覆盖。
- 从「结构解析」切走时**不回退**：选项不消失，保留用户的选择（PDF 等由后端 LLM 分层兜住）
- 各切块方式的参数默认值由 `GET /api/kbs/ingest-defaults` 供给（后端
  `ingestion/params.py` 是唯一来源），前端不再自带一份

### 8.3 怎么选

| 文档情况 | 建议 |
|---|---|
| Word / docx + 结构解析 | ✅ **首选**——层级由 OOXML 直读，精确，零额外成本 |
| PDF 等 OCR 产物 + 已配置「标题分层模型」 | ✅ 可用——层级经「编号规则 + LLM」还原后聚合 |
| PDF 等 OCR 产物 + **未**配置标题分层模型 | ⚠️ 效果有限——层级只能靠编号规则推断，无编号的标题会退化 |
| 没有标题结构的文档 | ❌ 不适用——整篇会聚成一个组，退化为普通切块 |
