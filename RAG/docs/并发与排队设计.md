# 并发与排队设计

图片摘要（以及所有入库任务）在**多用户同时使用**时的行为：谁先跑、谁排队、
资源怎么分。本文是这套机制的完整说明，含设计理由与实测数据。

代码位置：`backend/services/ingestion/service.py`（文档级闸门）、
`backend/services/image_summary.py`（请求级池）。

---

## 背景：为什么要并发，又为什么不能乱并发

图片摘要原本是**逐张串行**调用多模态模型。实测一份 148MB 的文档（483 张图引用、
其中 232 张要真正送模型）需要 **244 秒**——用户点完解析要等 4 分钟才看到"已入库"。

但直接把 232 张图一次性发出去是**不行的**：模型服务会被压垮，请求大面积超时。

而且这个系统是**多人共用**的：3 个用户同时点解析，如果每篇文档各自开 4 个并发，
就是 12 个请求砸向同一个模型——比单文档并发更危险。

**所以真正的设计目标是**：

> 让**在飞请求总数**恒定可控，同时保证**多篇文档之间公平推进**。

---

## 一、两级并发

```
用户A 触发解析 ─┐
用户B 触发解析 ─┼─→ ① 文档级闸门  ingestion.concurrency（默认 3）
用户C 触发解析 ─┤      最多 3 篇文档同时进入"解析"状态，超出 → 排队（可见）
用户D 触发解析 ─┘          ↓ 拿到槽位
                    ② 请求级池  image_summary_concurrency（默认 4）
                       所有**正在解析的文档共享**这一个池
                          ↓
                       多模态模型
```

**两级解决的是两个不同问题**：

| 级别 | 配置项 | 默认 | 解决什么 |
|---|---|---|---|
| 文档级 | `ingestion.concurrency` | 3 | 不让太多文档同时抢 CPU / MinerU / embedding |
| 请求级 | `image_summary_concurrency` | 4 | 控制砸向多模态模型的在飞请求数 |

两者都是**信号量**，都在系统配置页可调、改完即时生效。

**关键点**：请求级池是**全局共享**的（模块级变量，见 `image_summary._get_semaphore`），
不是"每篇文档各有一个"。若做成后者，3 篇 × 4 = 12 个请求就会同时压向模型。

---

## 二、单用户解析：怎么走

只有一篇文档在解析时，它**独占整个请求池**。

```
用户点「解析」
   ↓
① 文档闸门：当前 0 篇在跑 → 直接通过
   ↓
② 解析阶段（下载 → 解析 → 图片上传）        ~28 秒（148MB docx）
   ↓
③ 图片摘要阶段：
   筛选（跳过装饰性小图/超限图）→ 232 张待处理
   ↓ 按池容量 4 分批提交
   [图1 图2 图3 图4] 同时送模型 → 全部返回 → 再送下一批
   [图5 图6 图7 图8] …
   ↓  进度文案「图片摘要（n/232）」，n 为**已完成**张数
④ 切块 → 向量化 → 入库
```

**实测**（232 张）：摘要阶段 **约 135 秒 ≈ 1.72 张/秒**，全程无失败。

**为什么是"分批"而不是"一次全提交"**：见第四节。

---

## 三、多用户解析：怎么走

### 情况一：用户在闸门额度内（如 3 人同时解析，闸门 = 3）

三个人**都拿到槽位**，于是**同时**在跑，共享同一个请求池：

```
时刻      用户A(文档1)           用户B(文档2)           用户C(文档3)
──────────────────────────────────────────────────────────────────────
t=0      解析文档               解析文档               解析文档       ← 都过闸门
t=75s    图片摘要（n/232）      图片摘要（n/232）      图片摘要（n/232）
         └────────── 共享 4 个并发额度：每人约 1~2 张在飞 ──────────┘
t=290s   已入库                 已入库                 已入库         ← 相差不到 3 秒
```

**实测**（三文档同时触发、各 232 张）：摘要阶段各约 **213 秒**，
**总吞吐 3.27 张/秒**，三篇完成时间相差不到 3 秒。

> 注意：每人 213 秒 **比单文档独占时的 135 秒慢** —— 这是必然的，池子被三家分。
> 但换来的是**三个人同时完成**，而不是"一个人 135 秒、另两人干等 270 秒"。

### 情况二：超出闸门额度（如 4 人同时解析，闸门 = 3）

第 4 个人**排队**，前端状态列显示橙色 `🕐 排队中`：

```
时刻      用户A/B/C（在跑）                        用户D
──────────────────────────────────────────────────────────────
t=0      解析文档 …                               排队中（前面还有 3 个）
t=75s    图片摘要（n/232）…                       排队中（前面还有 3 个）
t=290s   已入库                                   图片摘要（n/232）   ← 拿到槽位
```

**排队位置是实时的**：前面一篇完成，后面的 N 自动减 1。

**两层行为小结**：

1. **文档闸门层面**：拿到槽位的才能进入"解析"状态；超出的排队等待，
   状态列可见（见第六节）。
2. **请求池层面**：所有**正在解析**的文档**共享**那 4 个并发额度 ——
   各自同时只有 1~2 张图在飞，但**总和恒不超过 4**，模型不会被压垮。

## 四、公平性怎么保证：分批提交

这里踩过一个坑，值得单独说。

### 坑：FIFO 队列被单篇文档占满

`asyncio.Semaphore` 是 **FIFO** 的。第一版实现是"一次性 `gather` 全部协程"：

```python
# ❌ 第一版：把本篇 232 个协程一次性提交
await asyncio.gather(*[_one(n, d) for n, d in jobs])
```

结果：文档 A 的 232 个协程全排在队首 → **A 独占池跑完，才轮到 B**。实测三篇
耗时精确成 **1:2:3** 倍（117s / 236s / 354s）——第 3 个用户要等 6 分钟，
比改造前的"各篇并行推进"还差。

**这类问题压测发现不了**（压测只跑单文档），只有真实多文档并发才暴露。

### 解法：按池容量分批，批间让出控制权

```python
# ✅ 现在：按池容量分批提交
batch = max(1, concurrency)
for i in range(0, total_jobs, batch):
    await asyncio.gather(*[_one(n, d) for n, d in jobs[i:i + batch]])
```

每批提交 4 个、等它们完成后**再提交下一批**。每批之间的 `await` 会让出控制权，
其他文档的批次就有机会进队列 —— 三篇文档的批次**交替进入 FIFO 队列**，
自然形成公平推进。

**效果**：三篇完成时间差从"1:2:3"变成"相差不到 3 秒"，且总吞吐不降。

## 五、结果正确性：并发不改变产物

并发只该影响**耗时**，不该影响**内容**。保证手段：

1. **每张图独立一次请求**（不是"一个请求塞多张图"）——后者才是会导致模型答串、
   图文对不上号的做法；
2. **结果按图片名存取**，不靠序号或位置传递：

   ```python
   done[name] = text            # 存：按图片名
   text = done.get(m.group(1))  # 取：按图片名
   ```
3. **回填按 markdown 原序**（`_IMG_REF_RE.sub`），与谁先完成无关；
4. **测试锁死**：`tests/test_image_summary_concurrency.py` 断言"并发 4 的产物与
   串行**逐字节一致**"，并逐张检查"每张图后面跟的是它自己的摘要"。

## 六、排队可见性

并发满时，后来者**不能是静默的** —— 否则用户以为没点上、反复点（后端会静默
忽略重复触发，更让人以为系统坏了）。

**实现**：排队期文档状态仍是"待解析"（`transition("parsing")` 在拿到槽位之后），
所以由进度接口**额外**返回排队信息：

- `_queued` 是**有序列表**（FIFO），排队位置 = 它在队列中的下标；
  因为信号量是 FIFO，位置越前越先轮到；
- `get_progress` 对排队中的文档返回 `排队中（前面还有 N 个）`；
- 前端状态列据此显示橙色 `🕐 排队中`，悬停看完整文案。

**位置是实时前移的**：前面一篇完成，后面的 N 自动减 1，无需额外刷新逻辑。

## 七、配置项

系统配置 → 入库并发（超管可调，改完即时生效）：

| 配置 | 默认 | 范围 | 说明 |
|---|---|---|---|
| `ingestion.concurrency` | 3 | 1~10 | 同时解析的**文档数**上限 |
| `ingestion.image_summary_concurrency` | 4 | 1~16 | 图片摘要的**请求**并发上限（跨文档共享） |

**默认值 4 的由来**（实测，单文档 16 张真实图片）：

| 并发 | 总耗时 | 吞吐 | P50 延迟 | P95 延迟 | 成功率 |
|---|---|---|---|---|---|
| 1 | 16.82s | 0.95 张/秒 | 1.06s | 1.69s | 16/16 |
| **4** | **5.95s** | **2.69 张/秒** | 1.42s | 2.12s | 16/16 |
| 8 | 5.34s | 3.00 张/秒 | 2.30s | 3.13s | 16/16 |
| 16 | 4.66s | 3.44 张/秒 | 2.98s | 4.66s | 16/16 |

- **1→4 是最大收益点**（吞吐 ×2.8）；
- 4→8 仅 +11%、8→16 仅 +15%，但**延迟翻倍**；
- 吞吐天花板 ≈3.4 张/秒是那台 9B 模型的物理上限，加并发突破不了；
- 16 并发零失败 —— 稳定性没问题，选 4 是拿"八成收益 + 低延迟"。

**配 1 = 回到改造前的串行行为**，作为随时可用的回退档位。

## 八、这套设计的边界（不做什么）

- **不是负载均衡**：没有优先级、加权、抢占，没有"重要文档优先"。是"限流 +
  分批让出形成的交错公平"，够用但不是严格公平调度；
- **单进程**：所有任务在同一个 asyncio 事件循环里，不存在"分发到多个 worker"；
- **模型是最终瓶颈**：无论怎么调并发，总吞吐受模型算力限制（本例 3.4 张/秒）。
  并发只让这个上限被更快地吃满，不提高上限；
- **摘要内容本身有随机性**：`temperature=0.1` 仍有波动，同一文档两次解析的摘要
  措辞会不同（随之切块边界可能差一位）。**这与并发无关**，串行也一样。
