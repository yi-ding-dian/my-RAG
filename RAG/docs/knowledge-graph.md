# 知识图谱功能原理

> 本文档说明 my-RAG 知识库"知识图谱"功能的生成原理、数据模型、检索增强方式与设计取舍。
> 对应代码：`backend/services/knowledge_graph_service.py`、`frontend/src/components/KnowledgeGraphTab.tsx`

---

## 一、总体流程（一图流）

```
文档（如 5 万字）
  │ ① 切块（每块约 500-800 字，与入库切块共用）
  ▼
┌────────────────────────────────────────────────────┐
│ 块1 → LLM 抽取：{"entities":[…], "relations":[…] }   │
│ 块2 → LLM 抽取（并发 3 同时进行）                     │
│ 块3 → …                                              │
│ （单块输入截断 1000 字，失败/超时跳过该块不阻塞入库）   │
└────────────────────────────────────────────────────┘
  │ ② 合并与消解（跨块同名实体对齐）
  ▼
实体去重合并（"艾伦·图灵"在块1/块9都出现 → 合成一个实体，count=2）
  │ ③ 持久化
  ▼
data/storage/graphs/{kb_id}.json（按知识库一个文件，无外部图数据库）
```

- **入口**：解析配置弹窗勾选"知识图谱"开关（默认关闭，开启提示 token 费用）
- **时机**：入库链路内同步构建（切块后处理阶段，与上下文检索增强并列）
- **思考模式**：可配置关闭/开启（默认关闭思考，抽取属简单任务，关闭后一份文档约 20 秒）

## 二、抽取原理（核心：LLM + 约束）

### 2.1 Prompt 设计

给模型的抽取指令是**结构化三元组抽取**：

```
从以下文本中抽取实体和关系，强制 JSON 输出：
{"entities":[{"name":"实体名","type":"类型","description":"一句话描述"}],
 "relations":[{"source":"源实体名","target":"目标实体名","type":"关系类型","description":"描述"}]}

实体类型白名单：人物 / 机构 / 技术 / 概念 / 事件 / 成果
关系类型白名单：提出 / 开发 / 发明 / 启动 / 导致 / 影响 / 属于 / 相关
约束：仅基于文本显式内容，禁止推断、禁止编造
```

### 2.2 关键设计

| 设计 | 原理 |
|---|---|
| **类型白名单** | 给模型划定抽取范围，防止自由发挥抽出一堆无意义实体；白名单可配置 |
| **强制 JSON 输出** | 结果可被程序可靠解析；另有兜底解析（```json 代码块 → 直接 loads → 平衡括号状态机），模型输出被截断时多策略修复 |
| **关闭思考**（thinking disabled） | 抽取任务简单，不开推理模式可显著提速（实测约 17 倍）并降低 token 消耗 |
| **单块输入截断 1000 字** | 单次调用小、便宜、模型上下文不爆 |
| **温度 0.1** | 抽取确定性，减少幻觉 |

### 2.3 并发与容错

- 并发 3（asyncio.Semaphore），单调用超时 60s
- **失败/超时/空结果 → 跳过该块**，绝不阻塞入库（实测 18/23 块成功也能产出可用图谱）
- LLM 未配置 / 配置失效 → 跳过整个图谱构建，入库正常完成

## 三、合并与实体消解

同一实体出现在多个块里，靠**名称规范化 + 去重合并**对齐：

```
名称规范化：
  - trim 空白
  - 全角 → 半角统一
  - 数字间空格压缩（PDF 提取常见："IEC 1 0 4" → "IEC104"）

合并规则（按 name + type 去重）：
  - count 累加（实体出现次数）
  - chunk_refs 追加（记录 文档id + 块序号 + 字符偏移，精确可跳回原文）
  - 描述合并截断（限制长度，不无限累积）
  - 关系 weight 累加
```

**幂等**：文档重入库时先清除该文档旧引用再合并，图谱不翻倍；删除文档（purge）时引用移除、无引用的实体/关系删除；删除知识库时整个图谱文件删除。

## 四、数据模型（存储结构）

```
data/storage/graphs/{kb_id}.json

{
  "kb_id": "…", "updated_at": "…",
  "docs": { "{doc_id}": {"name": "文档名", "chunk_count": 58} },
  "entities": [
    {
      "id": "e1", "name": "艾伦·图灵", "type": "人物",
      "description": "英国数学家，提出图灵测试",
      "count": 3,                                   # 出现次数（跨块累加）
      "chunk_refs": [                                # 挂接 chunks_meta 偏移契约
        {"doc_id": "…", "chunk_index": 5, "char_start": 123, "char_end": 140}
      ]
    }
  ],
  "relations": [
    {
      "id": "r1", "source": "e1", "target": "e9", "type": "提出",
      "description": "艾伦·图灵提出了图灵测试",
      "weight": 1.0,
      "chunk_refs": […]
    }
  ]
}
```

- **无外部图数据库依赖**（不引入 Neo4j），单文件 JSON 按知识库组织，人类可读
- 实体挂 chunks 的 `chunk_index + char_start/char_end` **与 chunks_meta 偏移契约完全一致**，前端可精确跳转定位原文

## 五、检索增强（查询时如何调用）

```
用户提问
  ↓
① LLM 从问题中抽取查询实体（如"图灵测试是什么" → "图灵测试"；关闭思考、8s 超时、失败返空不阻塞）
  ↓
② 图谱匹配：名称规范化后 精确 / 包含 双向匹配（≥2 字防误匹配）
  ↓
③ 1-hop 邻接扩展：匹配实体 + 邻居实体 + 两端都在子图内的关系
  ↓
④ 组装"知识图谱"来源的引用：
   【知识图谱实体】图灵测试(概念|判断机器是否具备智能的测试方法|1)
   【知识图谱关系】艾伦·图灵|提出|图灵测试|艾伦·图灵提出了图灵测试
  ↓
⑤ 注入回答的 [引用] 区（document_name="知识图谱"），与向量/BM25 检索并行，互不干扰 rerank
```

- **开关**：聊天设置"知识图谱增强"（默认开）；无图谱文件自动跳过，零成本
- **价值**：跨块/多跳关联问题（"图灵测试和专家系统有什么关系"）可从图谱关系路径直接给出线索

## 六、容错与成本

| 项 | 数值/行为 |
|---|---|
| 并发 | 3 |
| 单块超时 | 60s（抽取）；8s（查询抽实体） |
| 失败处理 | 跳过该块/降级，绝不阻塞入库与查询 |
| 实测耗时 | 关闭思考：23 块文档约 **20 秒**入库（开启思考约 6 分钟） |
| 实测成本 | 约 5.7 万 tokens/文档（deepseek-v4-flash，约 0.3-0.9 元峰谷价） |
| 实体挂接 | 全部实体带 chunk_refs（可跳原文） |

## 七、局限与后续增强方向

### 当前已知局限

1. **跨块远距离关系抽不出来**——"块 1 的实体 A 和块 20 的实体 B 有直接关系"但两者从未在同一块出现，建不了边（分块抽取的天然代价）
2. 名称消解是轻量级（规范化 + name/type 精确合并），"谷歌" vs "Google" 这类异构写法合并不了
3. 抽取质量依赖模型：关系抽取对推理依赖略高，关闭思考后关系数量约降 1/3（量级相当）

### 后续增强方向

| 方向 | 说明 |
|---|---|
| **gleanings 二轮补抽** | Microsoft GraphRAG 做法：对高密度实体再抽一轮跨块关系，成本约翻倍 |
| 社区检测与摘要 | Leiden 算法分组 + 每组生成社区摘要（Global Search 能力） |
| 名称消解增强 | 编辑距离 / 拼音 / embedding 相似度合并异构实体名 |
| 抽取并发提升 | 并发 3 → 更高，或换非推理模型进一步提速 |
| 力导向图增强 | 已有 ECharts 力导向图 + 实体搜索子网视图（1/2 跳切换） |
